# ADR-014: A holder is data on the tool bit

## Status
DRAFT

## Context

The simulator needs to know what is above the cutting edges: the shank, and the collet nut or chuck the **Tool Bit** is set in. A **Holder** hitting the **Stock** or the **Workholding** is a crash. Holders come in standard families (ER collets, router nuts) and shops add their own.

Options considered:

1. **A model file per holder.** Exact, but each check opens and recomputes a document.
2. **An outline as data:** (radius, height) points revolved about the **Tool Axis**. All a collision check needs; nothing is opened.
3. **Where it lives:** on the **Tool Controller**, or on the **Tool Bit**.

## Decision

A **Holder** is a `.fcholder` JSON file: (radius, height) points in millimeters from the face the bit comes out of, upward, revolved about the **Tool Axis**. Built-in holders ship with CAM (ER11 to ER50, ER8 to ER25 mini, router nuts); files in the user's CAM assets override them.

The **Holder** and the **Stickout** belong to the **Tool Bit**, not the **Tool Controller**: a bit is set in one holder at one stickout.

- The simulator draws the **Holder** and stops at a holder or rapid strike.
- The **Tool Bit** library update shows and updates the holder and stickout.
- A holder file that cannot be read counts as no holder, with a warning.

## Consequences

- Gains: collision checks with no extra documents; holder sets shared as small files.
- Costs: no exact holder model to show.
- Note: ADR-000 lists "tool holder" as a word to avoid for **Toolhead**. **Holder** here means the collet chuck or nut on the bit, never the spindle.
